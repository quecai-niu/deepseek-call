# 对话管理执行计划

## 架构目标

- 使用 Supabase Free 作为云端 PostgreSQL 和 Auth 服务。
- 所有业务操作都走本项目自己的后端 API。
- 前端只调用后端接口，不直接写入对话表，也不直接调用模型。
- 数据库完整保存每个对话从头到尾的消息历史。
- 每次请求模型时，只发送受上下文预算限制的最近消息；后续可加入对话摘要。

## 数据结构

- `profiles`：业务用户资料，关联 Supabase Auth 用户。
- `conversations`：对话元数据，包括归属用户、标题、创建时间、更新时间、归档状态。
- `messages`：每个对话的完整消息历史。
- `attachments`：为后续文件输入保留的文件元数据表。
- `tool_runs`：为后续联网搜索、检索、Agent 工具调用保留的执行记录表。
- `conversation_summaries`：为后续长对话摘要保留的表。

## 后端接口

- `GET /api/conversations`：获取当前用户的对话列表。
- `POST /api/conversations`：创建新对话。
- `GET /api/conversations/:id/messages`：读取指定对话的完整消息。
- `POST /api/chat`：保存用户消息、构建模型上下文、调用模型、保存助手回复。
- `PATCH /api/conversations/:id`：修改标题、归档或更新对话。
- `GET /api/health`：检查后端 Supabase/DeepSeek 配置状态。

## 上下文策略

- 数据库保存完整历史，不因为模型上下文限制而删除老消息。
- 模型请求包含：
  - system prompt
  - 后续可选的对话摘要
  - 在预算内的最近消息
  - 当前用户消息
- 第一版采用最近消息数和字符预算裁剪。
- 后续可增加自动摘要，把更早的消息压缩后加入上下文。

## 对话上限

- 软上限：约 500 条消息后提示建议开启新对话。
- 硬上限：约 1000 条消息后要求开启新对话。
- 老对话保留在历史列表中，不做真删除。

## 前端行为

- 显示对话列表。
- 提供“新对话”按钮。
- 选中老对话时加载历史消息。
- 发送消息时保持当前对话选中。
- 如果没有选中对话，首次发送时自动创建新对话。
- 等待或流式回复期间，消息渲染保持稳定。
- 默认使用 `deepseek-v4-flash`，前端旧缓存会一次性迁移到 flash。

## 验证方案

- 验证用户可以创建新对话。
- 验证消息刷新后仍能恢复。
- 验证选中老对话能恢复历史。
- 验证模型调用使用裁剪后的上下文，而不是无上限发送完整历史。
- 验证失败时不会静默丢失用户消息。
- 验证未配置 Supabase/DeepSeek 时页面能给出明确提示。

## 回滚方案

- 数据库结构通过 migration 管理，必要时可回滚新增表。
- 前端保留清晰的聊天入口，不把对话管理和消息 UI 写死在一起。
- 后端保留独立的 `/api/chat` 流程，后续可以替换数据库或模型供应商。
- 不擅自执行 `git add`，不改变暂存区边界。
